Railway — April 24, 2026 — Fix supabase-py rejection of sb_secret_ keys
========================================================================

ZIP:                railway-fix-sb-secret-20260424.zip
Deploy impact:      Railway call_handler + aria_agent services restart
Expected effect:    /health 500 errors stop; Aria answers calls again

---

THE BUG

After yesterday's Supabase key rotation to the new sb_secret_* format
(post-Vercel incident), Railway's call_handler started failing /health
with:

  supabase._sync.client.SupabaseException: Invalid API key
    File "supabase/_sync/client.py", line 64

Root cause traced via library source inspection: supabase-py v2.10.0
has a hardcoded JWT regex check at client.py:61-64:

  if not re.match(
      r"^[A-Za-z0-9-_=]+\.[A-Za-z0-9-_=]+\.?[A-Za-z0-9-_.+/=]*$",
      supabase_key
  ):
      raise SupabaseException("Invalid API key")

This regex REQUIRES at least one dot (the JWT structure). The new
sb_secret_* keys have no dots, so they fail the regex before any HTTP
request goes out. The rejection is entirely client-side.

This contradicts Supabase's documentation which claims "any version of
the library works with new keys." The docs are wrong — the library
source is the ground truth.

---

VERIFICATION

Tested in clean venvs across multiple versions:

  v2.10.0  rejects sb_secret_   ← what Railway currently runs
  v2.15.3  rejects sb_secret_   ← last version with the bug
  v2.16.0  accepts sb_secret_   ← FIRST version with the bug fixed
  v2.28.3  accepts sb_secret_   ← current stable (regex removed)

The JWT regex check was removed from client.py between v2.15.3 and
v2.16.0. v2.16.0 is chosen as the minimum-viable fix — smallest possible
version bump to reduce risk of unrelated behavior changes.

CHANGES

  Dockerfile.call_handler  line 11
    supabase==2.10.0  →  supabase==2.16.0
    (This is the file the call_handler Docker image actually uses.
     It has deps inlined via pip install, NOT a requirements.txt reference.)

  requirements.txt  line 10
    supabase==2.10.0  →  supabase==2.16.0
    (This file IS used by Dockerfile.aria_agent — COPY requirements.txt
     then pip install -r requirements.txt.)

  requirements.call_handler.txt  line 16
    supabase==2.10.0  →  supabase==2.16.0
    (Orphan file — not actually used by any Dockerfile. Updated anyway
     so if someone re-wires the Dockerfile later to use it, they get
     the right version.)

  call_handler_requirements.txt  UNCHANGED
    (Has `supabase>=2.3.0` already. Loose floor allows current stable.
     Another orphan — not wired to any Dockerfile. Leaving alone.)

  Dockerfile.aria_agent  UNCHANGED
    (Uses requirements.txt which was updated.)

No Python code changes. The supabase-py API surface used by call_handler.py
and aria_webhook.py (.from_(), .table(), .rpc()) is stable across all 2.x
versions and unaffected by the upgrade.

HONEST NOTES

1. My initial proposed fix in a prior conversation suggested
   supabase==2.15.3 as "a known-good version" without testing it.
   That version has the EXACT same bug. Had you deployed that fix,
   Railway would have come back with identical errors. This CHANGES
   doc reflects the verified fix version, not the guessed one.

2. User diagnosed the Python library as the culprit early on. I
   doubted the diagnosis because Supabase docs claimed library
   compatibility. The docs are misleading. The user was right.

3. Dockerfile.call_handler uses inline pip install, NOT the
   requirements.call_handler.txt file. Easy to miss on first look
   because the filename suggests it's the build input. It isn't.
