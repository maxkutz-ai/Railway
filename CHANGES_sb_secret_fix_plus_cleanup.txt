CHANGE 1 — supabase-py version bump (fixes /health outage)

THE BUG
After yesterday's Supabase key rotation to the new sb_secret_* format,
Railway's call_handler started failing /health with:

  supabase._sync.client.SupabaseException: Invalid API key
    File "supabase/_sync/client.py", line 64

Root cause: supabase-py v2.10.0 has a hardcoded JWT regex check at
client.py:61-64:

  if not re.match(
      r"^[A-Za-z0-9-_=]+\.[A-Za-z0-9-_=]+\.?[A-Za-z0-9-_.+/=]*$",
      supabase_key
  ):
      raise SupabaseException("Invalid API key")

This requires at least one dot (JWT structure). sb_secret_* keys have
no dots → regex fails → exception fires before any HTTP request.

VERIFIED FIX VERSION
Live-tested across multiple versions in clean venvs:

  v2.10.0   rejects sb_secret_   ← what Railway currently runs
  v2.15.3   rejects sb_secret_   ← last version with the bug
  v2.16.0   accepts sb_secret_   ← FIRST version with the fix
  v2.28.3   accepts sb_secret_   ← current stable

v2.16.0 chosen as the minimum-viable fix.

INTENTIONALLY NOT DELETED (user requested, Claude pushed back)

The cleanup list also asked to remove .python-version and Procfile
(no suffix). Both are kept for this session because:

  .python-version — contains "3.12". If Railway ever falls back to
    Nixpacks buildpacks (vs Docker), Nixpacks reads this file to pick
    Python version. Docker doesn't use it, but deleting it removes a
    fallback signal. Zero value to delete. Non-zero risk.

  Procfile (no suffix) — contains `worker: python aria_agent.py start`.
    If Railway's aria-agent service doesn't have "Dockerfile Path"
    explicitly set in Settings → Build → Dockerfile.aria_agent, it
    might fall back to Procfile to start the worker.

  User needs to verify in Railway dashboard that BOTH services have
  explicit Dockerfile paths configured in Settings → Build → Dockerfile
  Path. If yes, .python-version and Procfile can be deleted in a
  future session. If no, they are load-bearing.
